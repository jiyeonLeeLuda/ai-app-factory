## 2. W1에서 가져올 배움 (요약 — 회고가 원본)

- run1 실패의 정체 = **격차 오판**: 스펙이 "토큰 스트리밍"을 격차로 잡았으나 장면이 요구한 건 "다중 말풍선"이었다. → **격차(내가 배울 것)와 장면(제품이 요구하는 것)이 스펙 한 칸에 뭉쳐 있어서** 종이 위에서 못 걸렀다.
- 그래도 X·Z축에선 성공(어필거리·배움) — 호기심은 버그가 아니라 공장의 존재 이유. 아픈 건 Y축(수렴 2라운드)뿐.
- spec_prep(≈25분)은 낭비가 아니라 **QC 투자**. run2는 개입 0·자동검증 통과·2턴버그 방지로 first-pass 성공.
- **북극성 하나로 누르지 말 것** — Y축 편향. 축별 점수판.

## 3. 이 세션에서 심의할 열린 질문 (지연이 던진 것)

각 질문은 결론 전에 **"지금 결정할 데이터가 있나? 없으면 뭘 먼저 볼까"**를 먼저 짚는다. 답이 갈리면 feedback-share-deliberation 형식(① 고민 ② 선택지 장단점 ③ 기우는 쪽+확신 없는 이유)으로.

- **Q1. W2 스펙 작성을 돕는 커맨드/스킬을 추가할까?**
  - Y축 레버2("스펙 작성 대화를 질문 세트로 파이프라인화")의 구체화.
  - 만들기 전 **재사용 먼저 확인**: 이미 있는 스킬(`deep-interview`, `omc-plan`, `dd-map`, `plan`, `study-note` 등)이 스펙-인터뷰를 대신할 수 있나? 새로 짓는 게 정당한가?
- **Q2. 처음부터 풀 파이프라인은 무겁다 — 어느 무게로 시작하나?**
  - 후보 스펙트럼: (a) 템플릿 한 장 강화(가장 가벼움) → (b) 대화형 체크리스트 → (c) 스펙 인터뷰 스킬 1개 → (d) 다단계 워크플로/에이전트(가장 무거움).
  - 원칙: 무게는 **증거가 정당화할 때만** 올린다(n=1 상태). 손쉬움도 지표다.
- **Q3. 팩토리를 짓는다면 결국 어떤 형태가 되나?**
  - 스킬? 커맨드? 템플릿 묶음? 에이전트? 워크플로? — 최종 형태에 대한 방향을 잡되, **오늘 전부 확정하지 않는다.** "다음 한 스텝"만 정한다.

## 4. 심의 원칙 (이 세션의 가드레일)

- **축 충돌 시 우선순위**: Y(팩토리) 1순위 → X(JYP) 다음. Z는 부산물. (`factory-over-jyp-priority`)
- **측정선 오염 금지**: Y축 지표에 X·Z 활동이 섞이지 않게.
- **앞서가지 않기**: 이 세션은 "방식 결정"까지. W2 실제 스펙/코드는 별도 세션. (`scope-to-current-step`)
- **재사용 우선**: 새 스킬/커맨드/에이전트를 짓기 전에 기존 것으로 되는지부터.
- **소크라테스식**: 결론을 떠먹이지 말고, 지연이 판단하게 질문으로 예열.

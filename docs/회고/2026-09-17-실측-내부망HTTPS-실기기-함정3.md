# W2.5 실측 회고 — 내부망 HTTPS 실기기 함정 3개 (스펙이 놓친 것)

날짜: 2026-09-17. 성격: **팩토리(Y축) 회고** — 원샷 first-pass(자동 게이트 전부 통과) **이후**, 폰↔노트북 실기기 통화를 시도하며 드러난 함정. 자동으로 못 잡고 **실측에서만** 발현. [[three-axis-job-change-frame]] Y축(공정 개선).
맥락: 스펙 `docs/w2.5-spec.md`는 "카메라 = secure context → 내부망 HTTPS(mkcert)"까지는 선행조사로 잡았으나, 그 **하위 3개**를 놓쳤다.

---

## 0. 한 줄

**"내부망 HTTPS로 폰 접속"은 한 줄이지만, 그 안에 브라우저별 CA·기기 신뢰 절차·앱 쿠키 Secure라는 3개 벽이 숨어 있었다.** 셋 다 localhost 자동 게이트로는 절대 안 드러나고 실기기+IP+HTTPS 조합에서만 발현.

## 1. 함정 ①: iOS Chrome이 로컬 CA(mkcert)를 거부

- **증상**: 폰 크롬에서 `https://172.10.102.176:3000` 접속 안 됨. **카톡 웹뷰에서는 됨**(이게 결정적 단서 — 네트워크·서버·인증서는 정상, 크롬만의 문제).
- **원인**: iOS Safari·WKWebView(카톡 웹뷰 포함)는 **시스템 신뢰 저장소**를 써서 사용자 설치 mkcert CA를 신뢰한다. iOS Chrome은 사용자 설치 로컬 CA에 더 엄격해 거부.
- **해결**: **Safari로 접속**(시스템 CA 신뢰 + `getUserMedia` 정식 지원). 실기기 테스트 기본 브라우저 = Safari.
- **스펙이 왜 못 잡았나**: 선행조사가 "secure context면 카메라 열림"까지만 봤고, **브라우저별 CA 신뢰 차이**는 범위 밖.

## 2. 함정 ②: 아이폰 rootCA 신뢰는 2단계 + 확장자

- **증상**: "인증서 신뢰 설정" 화면은 있는데 **토글이 없음**.
- **원인**: 신뢰 토글은 **CA가 실제로 설치된 뒤**에만 목록에 나타난다. `.pem` 확장자는 iOS가 "설치할 인증서"로 인식을 잘 못 함.
- **해결**:
  1. rootCA를 **`.crt` 확장자**로 폰에 전송(AirDrop) — 인식률↑.
  2. **프로파일 설치**(설정 > 일반 > VPN 및 기기 관리).
  3. **신뢰 토글 ON**(설정 > 일반 > 정보 > 인증서 신뢰 설정) — **이 3단계를 다 해야** 함. 설치만 하고 신뢰를 안 켜는 게 가장 흔한 실수.
- **스펙이 왜 못 잡았나**: 사람 준비물에 "핸드폰 rootCA 신뢰 설치"라고 **한 줄**로만 적었다. 실제론 확장자·2단계 UI 절차가 있어 재현 가능한 단계로 못 박았어야.

## 3. 함정 ③: HTTPS 쿠키에 Secure가 없어 iOS 로그인 유실

- **증상**: 가입 화면에서 닉네임·이메일 입력 후 "시작하기" → **그냥 새로고침**(가입 화면 복귀). 통화까지 가지도 못함.
- **원인**: 서버는 정상(200 OK + Set-Cookie 발급 — curl로 확인). 그러나 쿠키가 `HttpOnly; SameSite=lax`뿐 **`Secure` 없음**(`secure: NODE_ENV==="production"` → dev에서 false). **iOS Safari는 HTTPS 페이지에서 Secure 없는 쿠키를 저장하지 않아** 로그인 세션이 유실 → 홈이 다시 /signup로 리다이렉트(=새로고침).
- **해결**: 이 앱은 **dev·prod 모두 HTTPS 전용**(server.ts https)이므로 `secure: true`로 고정. (`lib/session.ts`)
- **스펙이 왜 못 잡았나**: 스펙이 "카메라 = secure **context**"는 알았지만, **쿠키의 Secure 속성**은 별개 층인데 놓쳤다. 자동 게이트(localhost)도 secure:false로 통과해 안 드러남.

## 3b. 함정 ④(진짜 범인): Next dev가 폰 IP의 JS를 cross-origin 차단 (allowedDevOrigins)

- **증상**: 폰에서 가입 "시작하기" → 아무 메시지 없이 `/signup?`로 새로고침. **alert(진단 코드)조차 안 뜸.** 노트북(localhost)에서는 완전 정상(가입·쿠키·alert 다 됨).
- **원인**: **Next.js dev 서버가 폰(IP origin)의 dev 리소스 요청(`/_next/hmr`·JS chunk)을 cross-origin으로 차단**(Next의 dev 보안 기본값). → 폰에서 클라이언트 JS가 안 붙음(**hydration 실패**) → `'use client'` 폼의 `onSubmit`/`preventDefault`가 동작 안 해 **폼이 네이티브 GET 제출**(`/signup?`) → 로그인 자체가 시작도 안 됨.
- **해결**: `next.config.ts`에 `allowedDevOrigins: ["172.10.102.176"]` 추가 + dev 재시작. (production 빌드로도 우회되지만 이게 한 줄.)
- **결정적 단서**: `/signup?`(쿼리 없이 `?`만) 리다이렉트 = JS 없이 네이티브 폼 제출. + 노트북 정상/폰 실패 切分. + **서버 로그가 원인·해결법을 그대로 출력**("Blocked cross-origin request … add to allowedDevOrigins").

### ⚠️ 진단 삽질 기록 (정직 — 메타 교훈)

이 함정을 잡기까지 **틀린 추측 두 개를 거쳤다**:
1. "iOS Safari가 Secure 없는 쿠키를 버린다" → `secure:true`로 수정(§3). **부분적으로 맞지만 진짜 원인 아님.**
2. "router.replace가 쿠키보다 빠르다" → `window.location.href`로 수정. **역시 부차.**
- **curl로 "서버 무죄"(200+Set-Cookie)를 확定한 게 오히려 함정**이었다 — curl은 **JS를 실행하지 않으므로** 클라 hydration 실패를 원리적으로 못 잡는다. 서버는 정말 정상이었고, 문제는 **브라우저가 JS를 못 붙이는 것**이었다.
- **결정타는 서버 로그 한 줄.** 추측으로 코드를 두 번 고치는 동안, **관측 수단(dev 서버 콘솔)을 먼저 봤다면** 즉시 끝났다. → 교훈: **"서버 무죄"를 코드로 좁히기 전에 로그부터 본다.** (feedback-suspicion ① 관측 수단 우선)
- 단 §3(secure)·window.location 수정은 **HTTPS 앱의 옳은 기본값**이라 되돌리지 않고 유지(부차적이지만 예방으로 유효).

## 4. 근본 진단 — 왜 넷 다 실측에서야 나왔나

- 세 함정 모두 **localhost 자동 게이트로는 발현 불가**: ①②는 실기기+로컬CA, ③은 HTTPS+iOS Safari 조합에서만.
- 즉 **first-pass 자동 게이트 성공 ≠ 실기기 동작.** 스펙의 Acceptance가 "실기기 항목은 사람 몫"으로 분리해 둔 게 **정확히 이 층을 잡으라는 설계였고, 실제로 여기서 셋이 걸렸다.** (측정 스펙트럼: 조용한 실패를 실측이 걸러냄 — 설계대로 작동.)
- 공통 뿌리: 선행조사가 **"카메라 secure context"라는 한 점**은 깊게 팠지만, "내부망 HTTPS 실기기 접속"이라는 **여정 전체의 하위 함정군**(브라우저 CA·기기 신뢰 절차·앱 쿠키)은 조사 지도에 없었다.

## 5. 예방책 (다음 스펙·체크리스트 반영 후보)

- [ ] **내부망 HTTPS 앱의 세션 쿠키는 `secure: true` 기본**(HTTPS 전용이면 dev도) — 스펙 S4/보안 항목.
- [ ] **실기기 테스트 브라우저 = Safari 명시** + "iOS Chrome은 로컬 CA 거부" 경고 — 스펙 실측 절차.
- [ ] **사람 준비물의 "핸드폰 rootCA 신뢰"를 재현 단계로**: `.crt` 전송 → 프로파일 설치 → 신뢰 토글 ON(3단계), "설치≠신뢰" 명시.
- [ ] **내부망 실기기 dev 접속은 `next.config`에 `allowedDevOrigins: [<IP>]` 필수** — 없으면 폰 JS(hydration)가 통째로 막힘. (또는 실측은 production 빌드로.)
- [ ] **실기기 실측은 dev가 아니라 production 빌드 권장** — dev의 HMR·origin 제한·chunk 분할은 실측 환경이 아니다.
- [ ] **진단 순서 규칙: "서버 무죄"를 코드로 좁히기 전에 서버 로그부터 본다** — curl은 JS를 안 돌려 클라 hydration 실패를 못 잡는다.
- [ ] `docs/스펙-작성-체크리스트.md` 0b에 **"내부망 HTTPS 실기기 = secure 쿠키 + 브라우저별 CA + 실기기 브라우저 + allowedDevOrigins"** 추가.

## 인터뷰 한 문장 씨앗 (실무 트러블슈팅)

> "내부망 HTTPS로 모바일 실기기를 붙일 때 세 층에서 막혔습니다 — iOS Chrome이 로컬 CA를 거부해 Safari로 우회, rootCA는 설치+신뢰 2단계가 필요, 그리고 HTTPS인데 세션 쿠키에 Secure가 없어 iOS Safari가 쿠키를 버려 로그인이 유실됐습니다. curl로 서버가 정상 발급하는 걸 먼저 확인해 원인을 서버가 아닌 쿠키 속성으로 좁혔습니다."

## 핵심 못

- **"secure context"(카메라)와 "Secure 쿠키"(세션)는 다른 층**이다 — 하나를 조사했다고 다른 하나가 커버되지 않는다.
- **자동 게이트 성공은 실기기 동작을 보장하지 않는다.** 실기기 함정군은 Acceptance 사람 실측에서만 걸린다 — 그래서 그 분리 설계가 값을 했다.
- 진단 순서의 힘: **카톡 웹뷰=됨**(→ 네트워크 무죄), **curl 200+Set-Cookie**(→ 서버 무죄) 두 관측이 원인을 각각 "크롬"과 "쿠키 속성"으로 좁혔다.

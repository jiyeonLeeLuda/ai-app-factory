# W2.5 회고 — 실측 튜닝의 시행착오, 스펙에 무엇을 미리 박았어야 했나

날짜: 2026-09-17. 성격: **Y축(팩토리 절차 — 스펙 작성 방식) 회고**. [[three-axis-job-change-frame]] Y축의 연장, [[2026-09-16-팩토리-스펙작성방식-결정]]의 후속 교훈.
맥락: W2.5 원샷은 자동 게이트(typecheck/lint/build/매핑테스트/셀프콜 4/4)를 **한 번에 통과**했다. 그런데 그 뒤 사람이 실기기로 보면서 **10회 이상 왕복 튜닝**이 났다. 원샷이 "실패"한 게 아니라, **원샷이 손댈 수 없는 영역에서 결정이 안 돼 있었다**.

---

## 0. 한 줄 교훈

**자동 게이트는 "파이프라인이 살아있다"만 증명한다. "보기에 맞냐"는 0% 커버한다.** 이번 시행착오는 전부 후자에서 났고, 스펙이 그것들을 "사람 Acceptance로 미룸"이라고 **적어둔 채 미룬 게** 왕복의 뿌리였다. → 눈으로 봐야 정해지는 것들을 **원샷 전에 스펙이 강제로 결정**하게 해야 한다.

## 1. 무슨 왕복이 있었나 (압축)

| 영역 | 왕복 | 자동 게이트가 못 잡은 이유 |
|---|---|---|
| 캐릭터 프레이밍 | 얼굴→상반신→전신→**얼굴** (4번 뒤집힘) | fake device·headless는 "렌더 루프 도는지"만 봄, 화면 구도는 못 봄 |
| 팔/손 트래킹 | 추가했다 **철회**(팔이 몸통과 따로 놀아 어색) | 몸 없는 fake device는 expr=0, 매핑 품질 검증 불가 |
| "카메라 크게" | 내가 **상대 실영상**을 고쳤다가 → 실은 **캐릭터 렌더 카메라**였음 | "카메라"가 두 개(웹캠 / three.js) — 용어 모호 |
| "caller 전신" | 코드 문제로 의심 → 스크린샷 찍어보니 **stale 번들**이었음(코드 정상) | dev 핫리로드 아티팩트, 게이트 밖 |
| 역할 배정 | 입장 순서 기반 → "폰일 때만 캐릭터"처럼 뒤집힘 → **선택식**으로 | 게이트는 fake로 순서 고정이라 뒤집힘 안 드러남 |
| 권한 "허용 전 실패" | AbortError만 무시(틀림) → 로그로 진단 → **자동요청+early-return** 이 근본 | fake device는 프롬프트가 없어 재현 불가 |
| 좌우반전(거울) | 캐릭터 머리 → 상대 영상 → 자기 PIP (3번에 나눠 추가) | "거울이냐"는 사람 감각, 자동 판정 불가 |
| PIP 위치 | 우측 상단 → **하단**(폰 노치에 얼굴 가림) | 폰 노치는 데스크톱·헤드리스에 없음 |

## 2. 근본 원인 (패턴 5개)

1. **게이트의 착시** — "셀프콜 4/4 통과 = 완성"으로 읽히지만, 그건 연결·데이터흐름 생존일 뿐. expr 값이 전부 0(얼굴 없음)이었다는 걸 게이트 로그가 보여줬는데도, "됐다"는 신호로 과신됐다.
2. **시각/UX 결정을 스펙이 안 내림** — "얼굴 트래킹 영상통화"는 다음을 **결정하지 않았다**: 프레이밍 크기, 거울 여부, PIP 위치, 역할 배정 방식, 권한 트리거(자동/클릭). 전부 원샷 전에 정할 수 있었는데 실기기에서 하나씩 발견됐다.
3. **타깃 플랫폼(폰) 제약이 스펙에 없었다** — 앱의 실측 목표가 "핸드폰 내부망 HTTPS"인데, iOS 제스처 필수·노치·Secure 쿠키·allowedDevOrigins는 스펙에 한 줄도 없었다. 데스크톱 게이트만 통과하면 폰에서 줄줄이 터졌다.
4. **handedness(좌우)를 "이후"로 미룸** — 스펙은 "좌우반전·스케일 어긋날 수 있음, first-pass는 임계값까지"라고 적었다. 그런데 거울 방향은 **사람이 화면 보는 첫 3초에 걸리는** 것이지 "이후" 항목이 아니었다.
5. **도메인 용어 모호** — 이 앱엔 "카메라"가 2개(웹캠 / three.js 렌더 카메라), "영상"이 3면(내 PIP / 상대 큰 화면 / 캐릭터 캔버스). 한 단어가 여러 대상을 가리켜 지시가 오조준됐다(내가 두 번 엉뚱한 걸 고침).

## 3. 다음 스펙에 넣을 것 (핵심 — 반복 방지 체크리스트)

### 3a. "실물 확인 후 확정" 단계를 스펙에 명시
원샷 뒤 왕복을 **N번 → 1번**으로 줄이는 구조:
> 원샷은 **튜닝 가능한 first-pass + 노브(상수)**를 만든다. 그 뒤 **사람 리뷰 1회**가 아래를 한 번에 잠근다: 프레이밍 거리 / 거울 방향 / PIP 위치 / 역할 UX / 권한 트리거.

이번엔 이걸 하나씩 발견해서 10왕복이 났다. "어차피 눈으로 봐야 정해지는 것들"을 **묶어서** 한 리뷰에 몰면 됐다.

### 3b. 시각/UX 결정을 스펙에서 미리 못박기 (미결 = 왕복)
- **프레이밍**: 얼굴 클로즈업 / 상반신 / 전신 중 하나를 **선택해서 적는다**(+ 튜닝 노브 이름).
- **거울(handedness)**: 자기영상·상대영상·캐릭터 각각 거울 여부를 **표로** 못박는다.
- **PIP 위치**: 코너 지정(+ 폰 노치 회피 명시).
- **역할 배정**: 순서 기반 금지 — 명시적 선택/계정 기반으로 **결정적**이게.
- **권한 트리거**: 자동 vs 사용자 제스처 — **제스처 기본**(모바일 타깃이면 필수).

### 3c. 타깃 플랫폼 제약 섹션 (모바일이 타깃이면 필수)
iOS/모바일 체크리스트를 스펙에 박는다: getUserMedia 제스처 필수 · secure 쿠키 · 내부망 origin 허용 · 노치 안전영역 · 자동재생 unlock. (이번 `2026-09-17-실측-내부망HTTPS-실기기-함정3` 회고를 스펙 전제로 승격.)

### 3d. 도메인 용어집 한 줄
헷갈리는 다의어를 스펙 상단에 정의: "**렌더 카메라**(three.js) ≠ **웹캠**", "**캐릭터 캔버스** / **내 PIP** / **상대 큰 화면**". 지시·리뷰가 오조준 안 되게.

### 3e. 게이트의 한계를 스펙이 자백하게
"셀프콜 게이트는 **파이프라인 생존만** 증명(fake device는 expr=0). 표정 정확도·거울·구도·성능은 게이트가 **절대 못 잡음** → 반드시 사람 리뷰." 이 문장이 있으면 "게이트 초록=완성" 착시를 막는다.

## 4. 내 작업 방식 교훈 (결이)

- **guess-first를 두 번 했고 두 번 다 틀렸다**: (a) "허용 전 실패"를 getUserMedia reject로 단정(실은 자동호출+early-return), (b) "카메라 크게"를 상대 영상으로 단정(실은 렌더 카메라). 둘 다 **증상 단어에서 성급히 원인으로 점프**했다.
- **observe-first로 바꾸니 바로 잡혔다**: "caller 전신"은 **스크린샷 2장**으로 stale 번들임을 밝혔고(코드 안 건드림), 권한 버그는 **로그(`onFrame#1`)** 로 "프레임이 콜백까지 안 온다 → ref null"을 관측해 근본을 잡았다.
- **규칙화**: 증상이 모호하면 **고치기 전에 계측/관측**(로그·스크린샷). 특히 "X 전에 실패"류는 타이밍/생명주기 문제일 확률이 높으니 reject로 단정 금지. → [[evidence-over-generic-advice]] 의 실행판.

## 5. 한 문장 요약

이번 원샷은 **코드가 아니라 스펙이 얕았다**. 자동으로 못 잡는 "보기에 맞냐"(프레이밍·거울·PIP·권한·역할·모바일)를 스펙이 미리 결정했다면 10왕복이 1리뷰로 끝났다. 다음 스펙엔 **§3 체크리스트**를 넣는다.

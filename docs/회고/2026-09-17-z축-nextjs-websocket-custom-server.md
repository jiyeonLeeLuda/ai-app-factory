# Z축 배움 — Next.js에 WebSocket 붙이기 (custom server)

날짜: 2026-09-17. 축: **Z(빈 지식 채우기)** — W2 SPEC 작성 중 발견해 채운 지식.
전제: 이 문서는 **제품(W2 스펙)도 공정(팩토리)도 아닌 Z축 배움 기록**이다. 측정선 오염 방지를 위해 분리 ([[three-axis-job-change-frame]]).

## 몰랐던 것 → 채운 것

**오해**: "Next.js 웹 서버가 웹소켓도 알아서 다루겠지."

**사실**: Next.js **혼자서는 웹소켓을 못 다룬다.** App Router의 Route Handler(`app/api/.../route.ts`)는 **요청-응답 1회성** 모델이라, 연결을 오래 붙잡는 웹소켓을 담을 수 없다.

**구조 뒤집힘 (오늘의 핵심 깨달음)**:
- Next는 원래 **Node 위에서 도는 라이브러리**다.
- 그래서 내가 직접 **Node 서버(`server.ts`)를 만들고**, 그 안에서 Next의 요청처리기를 **불러서 쓴다**.
- 즉 큰 앱은 **내가 만든 Node 서버**이고, 그 안에 **Next가 화면 담당으로 얹혀** 있는 것. ("Next가 웹소켓을 다룬다"가 아니라 "Next를 품은 Node 서버가 웹소켓도 담는다")

```
브라우저 ──┬─ 일반 요청(HTML/API) ──▶ Next handler
           └─ /ws 연결(upgrade) ─────▶ ws 핸들러
              (둘 다 같은 server.ts = 문지기)
```

`server.ts`가 문지기: 들어오는 걸 보고 "너는 웹페이지 → Next, 너는 웹소켓 → ws"로 갈라 보낸다.

## 20년차 관점 비판 (양가감정 정리)

처음엔 "창의적 해결책 같다 + 근데 이 규모에 적당한지 모르겠다"는 양가감정. 정리하면:

**"창의적인가?" → ✗.** custom server는 Next가 **공식 지원하되 명시적으로 비권장**하는 경로다. 쓰면 자동 정적 최적화 off·Vercel 배포 불가·운영 직접 부담. **전형적인 "Next에 실시간 붙이는 첫 우회로"**일 뿐 — 창의적으로 느낀 건 처음 봐서.

**업계 3가지 길:**

| 방식 | 내용 | 적합 |
|---|---|---|
| ① custom server 합체 (W2 선택) | `server.ts` 한 프로세스에 Next+ws | 로컬 PoC·학습·소규모 |
| ② ws 별도 서비스 분리 | Next=Vercel, ws=상주서버(Railway/Fly) | **프로덕션 정석** |
| ③ 매니지드 실시간 | Ably·Pusher·Supabase Realtime 위임 | 운영 아웃소싱 |

**왜 프로덕션은 ②/③으로 떼나** — 웹소켓은 stateful·long-lived, 웹 서버는 stateless. 한 프로세스에 묶으면: (a) 웹 배포마다 진행 중 통화가 다 끊김, (b) 웹/통화 부하를 독립 스케일 불가, (c) 프로세스 하나 죽으면 통화 전부 죽음.

**"이 규모엔 적당한가?" → ✓ (확신 높음).**
- 목표가 "STT→LLM→TTS 왕복을 손으로 엮기"라 **한 프로세스가 디버깅·반복 압도적으로 빠름**. 분리는 오버엔지니어링.
- 위 약점 3개는 전부 **프로덕션 배포 시나리오** — W2는 "로컬 학습 PoC, 배포 Out of Scope"로 이미 잘라둠. 약점이 범위 밖.
- 휘발 설계(턴 히스토리 세션 메모리)와 "프로세스 죽으면 날아감"이 궁합 맞음.

## X축(면접) 자산으로 전환

이 트레이드오프를 말할 수 있으면 시니어 시그널:

> "실시간 음성은 custom server로 Next+ws를 한 프로세스에 합쳤다 — 로컬 학습 PoC라 디버깅 속도가 이득이었다. 프로덕션이면 웹소켓은 stateful이라 웹과 스케일 특성이 달라, ws를 별도 상주 서버로 분리하거나 Ably 같은 매니지드로 뺐을 것이다."

**핵심**: '이게 프로덕션 패턴이 아님을 알고 **의도적으로 단순화**했다'를 말할 수 있는 것 자체가 어필 포인트.

## 문제

가상 아티스트 "필립"과 팬이 **음성으로 통화**하는 앱. 채팅방(W1 재현) 위에 통화 화면을 얹어, 브라우저 마이크 → WebSocket → 서버 릴레이(STT→LLM→TTS) → 브라우저 순차 재생의 왕복을 손으로 엮는다. 통화는 휘발(DB 미저장), 턴 히스토리는 연결별 서버 메모리로만 유지. 이번 주 학습 초점은 **음성 왕복 파이프라인 + 클라 VAD + custom Node server(ws)**.

## 배운 것

- **AI**: 추론모델(gpt-5-nano)의 `reasoning.effort:minimal`은 채팅뿐 아니라 통화 LLM에도 그대로 필수 — 통합 테스트에서 응답 65자로 벙어리 아님을 직접 검증했다. 스트리밍 문장경계 즉시 TTS 태우기가 첫소리 지연의 핵심.
- **FE**: 브라우저 종속 API(getUserMedia/MediaRecorder/`<audio>`)를 `AudioCapture`/`AudioPlayer` 인터페이스로 잘라 웹 어댑터만 구현 → W2.9 RN 포팅 때 상위 통화 로직은 그대로 두고 어댑터만 교체 가능. autoplay는 진입 클릭에서 단일 `<audio>` unlock + 재사용으로 회피.
- **BE**: Next App Router는 ws를 직접 못 열어 custom Node server(http+`ws`, `tsx`)가 문지기 — 일반요청은 `handle()`, `/ws` upgrade만 ws로, 나머지 upgrade는 Next에 위임(HMR 유지). STT는 실시간 ws 전사가 아니라 **발화 단위 파일 전사**(클라 VAD가 발화 경계를 만들어 전송).
- **Product**: 통화 휘발(DB 미저장) 결정으로 원샷 자기검증 흔적이 없어, 전사·응답을 서버 stderr 개발로그로만 남기고 화면 자막은 없앰(순수 전화 경험). 검증은 별도 통합테스트 스크립트로 대체.

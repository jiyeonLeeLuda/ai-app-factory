## 측정 기준 (이 로그를 어떻게 판정하나)

CONTEXT.md + 스펙에서 가져온 기준. **로그 채우기 전에 먼저 본다.**

- **성공(first-pass)** = 완료 선언 직후 **스펙의 Acceptance Criteria 전 항목을 사람이 체크해 통과**. 하나라도 미달이면 first-pass 실패.
  - 자동 검증(typecheck/lint/build/prisma validate)은 AI가 실행해 증거로 남긴다.
  - 런타임 항목(스트리밍·가입·복원·톤)은 사람이 눈으로 확인한다.
- **개입(intervention)** = 완료 선언 **이후** 사람이 해결한 문제 1건 = 1회. 종류 5: 설계오류/구현버그/스타일/누락/진행넛지(넛지는 분리 집계). 앱 결함이 아닌 환경 마찰은 개입이 아니라 gotchas로 분리.
- **개선점** = 실패·개입에서 뽑은 **다음 스펙에 넣을 문장**. (실사용으로 드러난 격차 가설 오류 등)
- 판정 시점 주의: first-pass는 **원샷이 만든 것 vs 스펙-원문**으로 판정한다. 완료 후 새로 원하는 재설계(예: 다중 말풍선)는 first-pass 실패가 아니라 **제품 진화**로 분리 기록.

## 문제

가상 아티스트 "필립"과 팬이 실시간 대화하는 단일 스레드 채팅앱. 답변이 토큰 단위로 스트리밍되어 "말하는 느낌"을 만든다. 회원(비밀번호 없는 식별)·아티스트·대화방·메시지를 DB로 관리하고, 페르소나는 OpenAI `instructions`로 주입. 이번 주 학습 초점은 스트리밍 파이프라인(Claude/OpenAI 스트림 → 서버 → 클라 SSE).

### 완료 후 발견 (측정 스냅샷 — 이후 변경은 여기 아래로 분리)

원샷은 스펙대로 만들었고(위 개입 0), 아래는 **실사용으로 드러난 제품 판단** — 원샷 결함이 아니라 스펙/장면 재설계:
- **격차 가설 오류(핵심 배움)**: 장면(팬-아티스트 채팅)에 실제로 필요한 건 "토큰 타이핑"이 아니라 **문장 단위 다중 말풍선**(디어유 버블류)이었다. 스펙이 격차를 "토큰 스트리밍"으로 잡은 게 실사용에선 어긋남. → SSE는 유지하되 문장 경계로 잘라 말풍선 emit(B안)으로 UX 전환.
- **"생각중 ..." 표시**: 순차 점멸 애니메이션 요청(S1에 이미 있던 요구 — 원샷 산출물에 있었는지 확인 후 누락이면 별도 기록).

## 제품 진화 (완료 후, 측정과 분리)

원샷 측정(개입 0) 확정 후 진행한 재설계 — first-pass 실패가 아니라 실사용 기반 개선:
- **B안(문장 다중 말풍선)**: SSE 유지, 서버가 문장 경계로 잘라 문장당 저장·emit, 클라가 ~600ms 시차로 말풍선 + "..." 순차 점멸. (executor 구현)
- **버그1(해결)**: "..." 타이핑이 대기 초기(전송~첫 문장)엔 안 뜸 → `isStreaming` 내내 표시로 수정.
- **버그2(미해결, 재실행으로 처리)**: **2번째 응답부터 말풍선이 사라짐/blank**. 턴 간 큐·타이머·done 플래그 초기화 문제로 추정. hand-B 코드라 깊게 디버깅 대신 **스펙에 엣지로 박고 원샷 재실행**하기로(코드=버림, 스펙=자산).

## 실패 (원샷 후)

이번 주 가장 아팠던 실패 — 다음 스펙에 넣을 문장:
1. **격차 가설 오류**: 장면(팬-아티스트 채팅)에 필요한 건 토큰 스트리밍이 아니라 문장 다중 말풍선이었다. → 장면은 돌려봐야 격차가 맞는지 안다(스펙 전 프로토타입 가치).
2. **팬텀 준비물**: factory role을 만들었다 "생각"했지만 실제 없었다(P1010). → 사람 준비물은 검증 명령으로 확인 가능하게.
3. **의존성 RC 함정**: prisma가 8 RC를 잡아 클래식 워크플로우 붕괴. → 핵심 의존성은 버전 핀.
